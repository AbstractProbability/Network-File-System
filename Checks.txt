Backup idea:
Empty ss (no files/dirs in file_dir). Also known as potential backup ss, until it becomes a regular ss or backup ss.
Non-empty ss: an ss which is not an empty ss. Also known as regular ss.
Each ss has a flag: backed_up. 

Now when a regular ss connects it has its backed_up false. When an empty ss connects, it is called a potential backup ss. If there are any ss with their backed_up false, then this empty ss becomes the backup ss for one of them. If there is no ss with backed_up false, then the empty ss becomes a regular ss.

The regularity/backing up etc. is only within an ns session. So ss_2 is a backup for ss_1 only for the duration that the ns is up. After ns goes down and the ss_1 and ss_2 connect again, THEY NEED NOT BE BACKUPS OF EACH OTHER, EVEN IF THEY CONNECT ONE AFTER THE OTHER. For example, if ss_1 backed up its data into ss_2 in the first session, then ss_2 would join the second ns session as a non-empty ss so these would not be bcakups of each other. HOWEVER in the file indexing, a their common files will still have both of their data. If the files are different, it is arbitrary whose info file is used and whose data is given to the client. This is done in order to simplify the cases where in session 1, ss1 goes down -> file is updarted in ss_2 -> data is never re-updated in ss_1. So in session 2, the same file path will have different contents for each of them. So it can be arbotrarily chosen which ones info file is taken and which ones data is taken. It need not be the one with the latest info/data.

A server and its backup store the EXACT SAME DATA as much as possible. SO initially, when an empty ss becomes a backup ss for a regular one, all content in the regular one is replicated to the backup by a direct connection between them. Whenever a write/undo/create/info file update/createfolder etc... happens in either of them, it is synced to the other. In a session, an ss stores its backup's ip and port, and the backup stores its parent's ip and port. So that if one goes down, the other can keep serving and when the ss comes back up, the changes are synced across each other.

Also note that if an ss or its backup goes down, then it makes its backed_up false for the one that is up. SUppose before the downed ss comes up, another empty ss is connecting, then the currently alive ss does become a candidate for being selected to back up with the new empty ss. In this case, the alive ss, if selected, will become the parent ss for the new ss and the new ss backs up this ss. It doesnt matter if the alive ss was originally a regular ss or a empty ss. Now in case this does happen, and the ss that went down comes back up, then that ss simply becomes a new regular (or empty) ss connecting to the ns.

Note that the difference between "backup ss" and corresponding "parent ss" is blurred after the initial full sync. Each ss thinks that the other is "backing me up". If a change happens on one, it is replicated on the other. If the one that went down comes back up, then a re-sync happens. This is reflected in the above scenario also, when one of the ss goes down, the alive one doesnt think of itself as "I am the backup so I should wait for my parent" or "I am the parent so i can choose someone else to back me up". Its more like "My backup went down, I will recognise him when he comes up, but if another potential backer comes and I am selected, I wont deny the offer."

A little more clarification:
If a partner goes down, there are 2 paths for the survivor:
partner down -> partner up before an empty ss comes: Then re-sync with partner, because you know the partner (you stored their port and ip.)
partner down -> empty ss comes before partner: Then if you are chosen to pair with the empty ss, you take the chance and pair with it. You abandon your old partner. If you are not chosen to pair with the empty ss, you wait until you are chosen to pair with some empty ss or your partner comes back up.
